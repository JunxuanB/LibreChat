# Unattended MCP credential capability matrix (working assessment)

**Status:** Code-backed inventory, not a claim that any third-party provider has passed an offline-grant review. Related to #16157. [Agent invocation authority](./unattended-agent-invocation.md) is a separate, prerequisite release gate. An agent identity token, an MCP resource token, and an OpenID browser-login token have different issuers and audiences; none can be substituted for another.

## Selecting the first integration

**No OBO provider is yet verified as safe for offline use.** Do not designate the browser-login `refresh_token` as the reference provider. A standards-based direct MCP OAuth server that issues an MCP-specific refresh grant is the nearest _code-backed_ candidate for validating the identity and consent boundary; it does **not** by itself fix OBO in #16157. A separate OBO reference provider is selectable only after its owner confirms an explicitly consented, renewable upstream credential with the right audience and scopes, its issuer's offline/revocation semantics, and acceptable handling after logout. If those conditions fail, publish an unsupported-provider outcome instead of fabricating unattended access.

For each concrete candidate, collect a redacted test fixture and record: issuer and resource audience; supported authorization/refresh flow; which principal consented; effective scopes and allowed read/write tools; refresh lifetime and rotation/reuse rules; grant revocation/disconnect API; multi-tenant and self-hosted fit; and what the owner sees on missing grant versus transient outage. No provider is marked **supported** based solely on a config schema, a successful browser call, or a returned `refresh_token`. Third-party/provider assertions must be checked against current provider documentation and an actual consent/refresh/revocation test before a provider is selected.

## Release and verification gates

1. First land the two-mode invocation authority contract with explicit consent/role and a self-hosted verifier. A valid authenticated workload and a verified provider grant are **both** necessary for new unattended MCP access. Existing Scheduled Chats keep their current admission and recovery semantics.
2. Add an opt-in, server-side grant resolution boundary. Key its authority to user or agent, tenant, root agent, MCP server identity, provider issuer/resource and approved scopes. Recheck live policy at preflight, at the last tool-use boundary, and after resume/handoff. The per-user OAuth token store is an implementation reference, not consent or proof of this binding.
3. Use one verified provider end to end in Scheduled Chats: explicit authorization, logout, restart, preflight, actual tool call, reconnect, resumed approval, across-replica rotation and revocation between admission and use. Exercise unavailable store/IdP, invalid scopes, cross-tenant and autonomous-denial cases. Verify a supported self-hosted deployment. Do not expand to events, Agents API, subagents or channels until each entry point passes the same gates.
4. Coexistence requires new-mode deliveries to be consumed only by capable workers. Rollback disables new grants/new mints and preserves legacy schedule and direct-MCP OAuth behavior; it must not leave old workers interpreting an authority-free delivery as newly authorized. Closing #16157 requires a supported OBO path to work unattended, not just diagnostic or direct-MCP OAuth coverage.
